Triage Flow Architecture

agentflow is a small engine that runs triage flows over items fetched from a source. This page describes its parts: the container it runs in, the four plugin folders, the flow as a graph, what is stored, and the pages, API and commands.

In short

One image, one processdocker compose up starts one container. One process in it serves the pages and the API, keeps the schedules and runs the flows. There is no queue service.
The flow is the unitA run is always a run of one flow. It ends with a report in the run folder. The engine sends nothing anywhere.
Source hands over, flow accepts, engine routesA source says how items are got and what it writes. A flow says which source it accepts, which of its items, and when. The engine fetches, checks and routes.
A graph with bounded loopsA flow compiles to stages joined by pass edges and fail edges. A loop exists only on a fail edge, and tries bounds it.
Agents inside, scripts besideAgents run in the engine's process on Pydantic AI and get only the tools they list. Scripts are plain child processes in the same container.
A folder per itemEvery stage reads and writes the item's work folder. It is the hand-over between stages and the evidence afterwards.
Facts stored, status derivedOne SQLite file holds runs, items, tries, verdicts and events. The pages, the API and the CLI read the same rows, so they agree.

How it runs

The engine runs inside one Docker image, built from the Dockerfile at the project root. Nothing of yours is in the image. compose.yaml attaches the settings, the plugins and the data folder when the container starts.

Each docker compose run is a container of its own on the same data/; the pages show its runs, because they read the same store. To give scripts or MCP servers another program, add it to the apt-get install line of the Dockerfile and build the image again.

compose.yaml

services:
  agentflow:
    build: .
    image: agentflow
    init: true                          # ends what a stopped script leaves behind
    ports: ["127.0.0.1:8321:8321"]      # this machine only: there is no sign-in
    environment:
      TZ: ${TZ:-UTC}                    # schedules are read in this time zone
    env_file:
      - path: .env                      # model keys, and the secrets granted to plugins
        required: false
    volumes:
      - ./agentflow.yaml:/work/agentflow.yaml:ro
      - ./plugins:/work/plugins:ro      # flows, agents, tools, sources
      - ./data:/work/data               # runs, reports and the database
      # - ~/code/product:/mnt/product:ro   # any other folder your scripts read

What the container protects

  • The host. The container is the boundary between scripts and the machine. A script sees the image and the attached folders, and nothing else of the machine.
  • The port. 8321 is bound to 127.0.0.1 only. A change through the API needs the header X-Agentflow: 1.
  • What a script is handed. Its environment holds PATH, LANG, AGENTFLOW_FLOW_DIR, AGENTFLOW_ITEM_ID, AGENTFLOW_TRIAL in a trial, and the secrets granted to its plugin under grants: in agentflow.yaml. A source's fetch script gets PATH, LANG, AGENTFLOW_OUT (its output folder) and its granted secrets. A tool's health script gets what a call of the tool gets. Model keys are not passed on.
  • Stopping. A script starts behind agentflow/guard.py in its own process group. The group is stopped when the script passes 120 seconds, when its item runs out of time, when its run is cancelled, and when the engine goes away.
  • Agents. An agent has no shell. Its file tools stay inside the item's folder: no absolute path, no .., no symbolic link, no writing the engine's files.

What it does not protect

Inside the container a script is a plain child process. It can read whatever is mounted in the container, and it can reach the network.

  • Nothing separates one script from another. A script runs as the same user as the engine.
  • A script can read agentflow.yaml, every plugin, and all of data/: other items, other runs, the database. It can write anywhere in data/.
  • There is no network rule per plugin. grants: names secrets only: it decides what a script is handed, not what it can reach.
  • No plugin file mentions Docker. Every flow shares the one image, and compose.yaml sets no CPU or memory limit.
  • An MCP server is started by the MCP client, not behind the guard. A script that moves itself to another session ends when the container does.

# plugins/flows/vuln-triage/flow.yaml
source: security-tickets
schedule: weekdays 07:00

stages:
  - id: gather
    run: scripts/gather.sh

  - id: analyse
    agent: origin-analyst
    check: scripts/chain-cites-files.py
    done_when: The origin is stated, and every link in the chain cites a file in the work folder.

  - id: fix
    done_when: The fix names a version or an image tag that candidates.json lists as fixed.

  - id: report
    done_when: report.md covers origin, chain, fix and evidence, and agrees with the earlier stages.

fix and report name no run and no agent, so the default agent does them, each following its stages/<id>.md. For a named agent that file is optional and is added to the agent's method. For a script stage it is documentation.

description: Find a package in a saved package list. Returns version and layer.

# plugins/sources/security-tickets/source.yaml
description: Open security tickets from the tracker.
run: ./fetch.sh
output: tickets.json

A tool with mcp: [command, …] in place of run is an MCP server. It is started in the item's folder when an agent run begins and stopped when that run ends. The agent gets every tool the server offers, named <plugin>_<tool>. No plugin in the project uses it.

limits in a flow may set at_once, minutes_per_item and cost_per_run_usd. Left out, the values in agentflow.yaml apply.

The contract between a source and a flow

WhoSaysThe engine
Sourcerun: how and where the items are got. output: the JSON file its script writes into the fetch's own folder, given in AGENTFLOW_OUT. fields: what every item has.Runs the script with the source's granted secrets. Reads the file: a JSON list of objects, each with a text id made of letters, digits, ., _ or -, no id twice, every listed field present. Anything else is a failed fetch, and no flow gets an item.
Flowsource: the source it accepts. where: a field and the value, or list of values, an item must have, for example where: {severity: [high, medium]}. schedule: when.Refuses a where on a field the source does not list. Hands the flow only the items that match. Flows on the same source that come due in the same slot share one fetch.

A source has no schedule and starts nothing: it is fetched when a flow that accepts it starts. A tool script gets its args in order as separate values, runs in the item's folder, and what it prints is the tool's answer. Its health script exits with 0 when the tool works; an MCP server is healthy when it starts and lists its tools. The server checks every tool when it starts, every five minutes and on request, and keeps the last answer. Every agent also gets list_files, read_file, write_file and ask_for_person; a reviewer gets no write_file. An agent run is capped at 20 model calls. A run copies the plugin files its flow uses into its own folder and executes from that copy.

The flow as a graph and the stage loop

agentflow/graph.py compiles the list in flow.yaml to a graph. The engine walks that graph, a resumed item is placed on it, and the pages draw it. agentflow/stages.py takes one item along it.

Two kinds of edge

  • Pass. An accepted stage goes to next.
  • Fail. A rejected stage goes to on_fail: to itself, which tries again with the reason, or to an earlier stage, which runs again with the reason while the item works its way forward again.
  • An agent is told its own rejected tries, and the rejections of later stages that sent the item back since it last ran. A script is told nothing; it is run again.
  • A stage has one way forward and one way back. There is no branching on content, no parallel stages and no flow inside a flow.

What compiling refuses

  • A stage with no id, one id used twice, or a stage called end.
  • next or on_fail naming something that is not a stage.
  • A loop on pass edges, and a stage nothing leads to.
  • on_fail on a stage with nothing that can fail, or naming a later stage.
  • tries outside 1 to 5.
one try of one stage:   do ──→ check script ──→ reviewer ──→ decide      # the first fail ends the try
What happens in a tryThe item
Every validation passes, or the stage has nonefollows the pass edge
A check or a reviewer fails, and the stage has tries leftfollows the fail edge, with the reason
Out of tries · a reviewer asks for a person · a reviewer errors · the agent calls ask_for_personends as needs a person
A stage script exits with an error · a model call failsends as failed
A stage script exits with 78ends as done; the remaining stages are skipped
minutes_per_item is used up · the run has spent cost_per_run_usd · the run is cancelledends as timed out stopped at cost cap cancelled

Nothing passes by default. Only a try that validation rejected counts against tries; a try cut short by a stopped process does not. The reviewer is a separate agent run with read-only file tools and no memory of the work.

What starts a run

A run is always a run of one flow. A person starts it, or the flow's own schedule does. A source starts nothing.

StartHowWhat happens
A personRun on the flow's page · POST /api/flows/{flow}/run · agentflow run <flow>The flow's source is fetched, and this flow alone runs over the items it accepts.
A person, every itemRun all again on the flow's page · the same request with {"force": true} · agentflow run <flow> --forceThe same, and nothing is carried over.
A scheduleschedule: in flow.yaml, switched on with the switch on the flow's page, POST /api/flows/{flow}/schedule or agentflow schedule on <flow>The flow's source is fetched and the flow runs. Flows on one source that are due in the same slot share the fetch. agentflow serve keeps the schedules and looks every 30 seconds. A schedule is off until it is switched on. Missed slots count as one.
A trialagentflow try <flow> [--item ID]One item through the real stages, in a run folder of its own. Stage scripts and tools get AGENTFLOW_TRIAL=1 and no granted secrets. A trial does not count as done.
  • The order of a run. Fetch the source into its own folder, check what it handed over, queue the items the flow accepts, work up to at_once of them in parallel, render the report, end the run.
  • Carried over. An item whose content is the same, and that ended as done or needs a person in an earlier run of this flow, is not worked again. Its row points at the earlier folder, and it costs nothing.
  • Refused at the start. A flow that does not pass its checks, and a flow that uses a model whose key is not set.
  • The report is the output. A run ends with report/index.html and one page per item in its folder. The engine sends nothing anywhere. Posting a result somewhere is a flow's own stage script or tool, with a granted secret.

Models

# agentflow.yaml
models:
  luna:
    provider: openai            # openai | litellm
    name: gpt-6-luna
    api_key_env: OPENAI_API_KEY # the variable, never the key
    api: responses              # responses | chat
    reasoning: low              # none | low | medium | high
model: luna                     # the platform default
limits:
  at_once: 4
  minutes_per_item: 10
  cost_per_run_usd: 2.00
grants: {}                      # e.g. sources/security-tickets: {secrets: [TRACKER_TOKEN]}
  • A model is a named entry under models:, with its own key variable. A litellm entry also takes base_url.
  • Picked in this order: model: on the stage, in the agent's AGENT.md, in flow.yaml, then the platform default.
  • A reviewer uses its own agent's model, then the flow's, then the default.
  • Keys come from the environment. agentflow/agents.py is the only module that knows about providers.
  • The pages show no global model. The model is shown on the flow, the stage, the agent, and each try in the trace.
  • --stand-in swaps in a scripted model that needs no key and costs nothing. It only knows vuln-triage.

What is stored

data/
├── db/agentflow.db          # the store: SQLite, WAL
├── fetches/
│   └── <date>-<n>-<source>/ # what one fetch wrote, as it wrote it
└── runs/
    └── <date>-<run id>/     # one folder per run or trial
        ├── plugins/         # the plugin files as the run first saw them
        ├── items/
        │   └── <item id>/   # the item's work folder
        │       ├── events.jsonl  # what happened to this item
        │       ├── attempts/     # <stage>-<n>.prompt.md: what each try was told
        │       ├── verdicts/     # <stage>-<n>.md: what each validation said
        │       └── …             # the files the stages wrote
        └── report/          # index.html, <item id>.html

Every name here is defined once, in agentflow/layout.py. The store keeps folders relative to data/, so the data folder can be moved. events.jsonl, attempts/ and verdicts/ belong to the engine: an agent's write_file refuses them. A run id starts with r_, a trial's with t_.

TableOne row per
schedulesFlow with a schedule: on or off, and when it is next due.
fetchesFetch of a source: its folder, outcome and item count. Unique on source and slot, so a slot is fetched once.
healthTool: whether its last check passed, what it said, and when.
runsRun of one flow: source, fetch, plugin hash, trial, folder, last sign of life, cancel request, what it is a retry of.
itemsItem in a run: fingerprint, folder, how it ended and why, where it was carried from, the item as fetched.
attemptsTry at a stage: who did it, start, end, outcome, model calls, tool calls, tokens, cost.
verdictsValidation of a try: by whom, pass or fail, the reason, whether a person is needed.
eventsThing that happened, in order: run, item, stage, type, data. Append-only.

Facts go in and status is worked out when asked, in agentflow/status.py. Claiming an item, ending an item and taking over a run are single conditional updates, so there is one winner. A cost that was not recorded is not zero: it shows as a dash, or as ≥ a partial sum.

Recovery

Nothing in agentflow/recovery.py acts by itself. The watchdog records; a person or a command decides.

PartHow it worksCommand · endpoint
Sign of lifeThe process doing a run writes a time to the run's row every 5 seconds. A run with no ending and no sign of life for 60 seconds shows as interrupted.
WatchdogEvery 15 seconds inside agentflow serve, and at the start of a resume or a cancel. It closes the open tries of a quiet run as interrupted and adds an event. It never resumes and never cleans up.
ResumeTakes over an interrupted run. A run that is alive or finished is refused. An item that had ended is left alone. An unfinished item is put back on the graph where its latest try left it, in its own folder, with the reasons of its rejected tries.agentflow resume <run> · POST /api/runs/{run}/resume · Resume on the run's page
RetryFor an item that has ended. A new run of that one item, with the plugin files as they are on disk. It starts at the stage the item stopped at, or at the first stage if the item was done. Its folder starts as a copy of the old one, and the earlier stages are kept. The old run is not changed.agentflow retry <run> <item> · POST /api/runs/{run}/items/{item}/retry · Retry on the item's page
CancelIn a live run, a running stage script or check script is stopped within half a second and its item ends as cancelled. An agent finishes its try, then its item stops. A run whose process is gone is closed on the spot. Folders are kept.agentflow cancel <run> · POST /api/runs/{run}/cancel · Cancel on the run's page

Pages, API and CLI

FastAPI renders the pages on the server from Jinja2 templates. A page of a run that is still going follows one server-sent event stream and asks for its changed part again. The sidebar reads Runs, then Design: Flows, Agents, Tools, Sources, then System: Settings. Under them, on every page, is Needs attention: plugin files to fix, a flow that could not start, a failing tool, an interrupted run, and items of a flow's latest run that need a person.

Tabs are addresses: /runs/{run}/trace, /flows/{name}/files. A run's report is at /runs/{run}/report/index.html. There is no sign-in.

agentflow check                        # plugin files, settings, tool health
agentflow try <flow> [--item ID]       # a trial of one item
agentflow run <flow> [--force]         # fetch the source, run the flow
agentflow schedule [on|off <flow>]     # show or switch schedules
agentflow serve [--port 8321]          # pages, API, schedules, tool health
agentflow show                         # recent runs
agentflow show <run> [item] [--follow] # what a run did and cost
agentflow resume <run>   agentflow retry <run> <item>   agentflow cancel <run>

try, run, resume, retry and serve take --stand-in. In the container, put docker compose run --rm in front of a command.
