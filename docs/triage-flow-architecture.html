Triage Flow Architecture

agentflow is a small engine that runs triage flows over items fetched from a source. This page describes its parts: the container it runs in, the four plugin folders, the flow as a graph, what is stored, and the pages, API and commands.

In short

One image, one processdocker compose up starts one container. One process in it serves the pages and the API, keeps the schedules and runs the flows. There is no queue service.
The flow is the unitA run is always a run of one flow. What a run puts out is written by the flow's own script into the run's output folder. The engine renders nothing and sends nothing anywhere.
Source hands over, flow accepts, engine routesA source says how items are got and what it writes. A flow says which source it accepts, which of its items, and when. The engine fetches, checks and routes.
A graph with bounded loopsA flow compiles to stages joined by pass edges and fail edges. A loop exists only on a fail edge, and tries bounds it.
Agents inside, scripts besideAgents run in the engine's process on Pydantic AI and get only the tools they list. Scripts are plain child processes in the same container. A stage's work can also be handed to Codex or Claude Code.
A folder per itemEvery stage reads and writes the item's work folder. It is the hand-over between stages and the evidence afterwards.
Facts stored, status derivedOne SQLite file holds runs, items, tries, verdicts and events. The pages, the API and the CLI read the same rows, so they agree.

How it runs

The engine runs inside one Docker image, built from the Dockerfile at the project root. Nothing of yours is in the image. compose.yaml attaches the settings, the plugins and the data folder when the container starts.

What the container protects

  • The host. The container is the boundary between scripts and the machine. A script sees the image and the attached folders, and nothing else of the machine.
  • The port. 8321 is bound to 127.0.0.1 only. A change through the API needs the header X-Agentflow: 1.
  • What a script is handed. Its environment holds PATH, LANG and what the engine tells it: AGENTFLOW_HOME, AGENTFLOW_FLOW, AGENTFLOW_FLOW_DIR, AGENTFLOW_RUN, AGENTFLOW_OUTPUT (the run's output folder), AGENTFLOW_ITEM_ID for an item's scripts, and AGENTFLOW_TRIAL in a trial. A source's fetch script gets AGENTFLOW_HOME and AGENTFLOW_OUT (its output folder). Model keys are not passed on, and there is no way yet to hand a script a secret.
  • Stopping. A script starts behind agentflow/workers/guard.py in its own process group. The group is stopped when the script passes script_seconds (120 unless set), when its item runs out of time, when its run is cancelled, and when the engine goes away.
  • Agents. An agent has no shell. Its file tools stay inside the item's folder: no absolute path, no .., no symbolic link, no writing the engine's files.

What it does not protect

Inside the container a script is a plain child process. It can read whatever is mounted in the container, and it can reach the network.

  • Nothing separates one script from another. A script runs as the same user as the engine.
  • A script can read agentflow.yaml, every plugin, and all of data/: other items, other runs, the database. It can write anywhere in data/.
  • There is no network rule per plugin, and no secret is handed to a script.
  • No plugin file mentions Docker. Every flow shares the one image, and compose.yaml sets no CPU or memory limit.
  • A coding CLI that does a stage has a shell of its own. Codex is started with its sandbox set to keep writes in the item's folder, and Claude Code accepts edits in the folder it starts in; the engine does not verify either.
  • An MCP server is started by the MCP client, not behind the guard. A script that moves itself to another session ends when the container does.

A tool with mcp: [command, …] in place of run is an MCP server. It is started in the item's folder when an agent run begins and stopped when that run ends. The agent gets every tool the server offers, named <plugin>_<tool>. No plugin in the project uses it.

limits in a flow may set any key of the platform's limits: at_once, minutes_per_item, cost_per_run_usd, script_seconds, model_calls, tries and the text sizes. Left out, the values in agentflow.yaml apply.

The contract between a source and a flow

WhoSaysThe engine
Sourcerun: how and where the items are got. output: the JSON file its script writes into the fetch's own folder, given in AGENTFLOW_OUT. fields: what every item has.Runs the script. Reads the file: a JSON list of objects, each with a text id made of letters, digits, ., _ or -, no id twice, every listed field present. Anything else is a failed fetch, and no flow gets an item.
Flowsource: the source it accepts. where: a field and the value, or list of values, an item must have, for example where: {severity: [high, medium]}. schedule: when. finish: a script of the flow that runs once when every item has ended and writes what the run puts out.Refuses a where on a field the source does not list. Hands the flow only the items that match. Flows on the same source that come due in the same slot share one fetch.

A source has no schedule and starts nothing: it is fetched when a flow that accepts it starts. A tool script gets its args in order as separate values, runs in the item's folder, and what it prints is the tool's answer. Its health script exits with 0 when the tool works; an MCP server is healthy when it starts and lists its tools. The server checks every tool when it starts, every health_every_seconds (five minutes unless set) and on request, and keeps the last answer. Every agent also gets list_files, read_file and write_file; a reviewer gets no write_file. An agent sees earlier runs only when its tools list the plugins history and history-file, which wrap agentflow history. An agent run is capped at 20 model calls. A run copies the plugin files its flow uses into its own folder and executes from that copy.

The flow as a graph and the stage loop

agentflow/plugins/graph.py compiles the list in flow.yaml to a graph. The engine walks that graph, a resumed item is placed on it, and the pages draw it. agentflow/stages.py takes one item along it.

Two kinds of edge

  • Pass. An accepted stage goes to next.
  • Fail. A rejected stage goes to on_fail: to itself, which tries again with the reason, or to an earlier stage, which runs again with the reason while the item works its way forward again.
  • An agent is told its own rejected tries, and the rejections of later stages that sent the item back since it last ran. A script is told nothing; it is run again.
  • A stage has one way forward and one way back. There is no branching on content, no parallel stages and no flow inside a flow.

What compiling refuses

  • A stage with no id, one id used twice, or a stage called end.
  • next or on_fail naming something that is not a stage.
  • A loop on pass edges, and a stage nothing leads to.
  • on_fail on a stage with nothing that can fail, or naming a later stage.
  • tries below 1.
one try of one stage:   do ──→ check script ──→ reviewer ──→ decide      # the first fail ends the try
What happens in a tryThe item
Every validation passes, or the stage has nonefollows the pass edge
The agent ends with failedends as failed, with the agent's reason. Its own decision; no further try.
A check or a reviewer fails, and the stage is under its ceiling of triesfollows the fail edge. On the same stage, the reason goes back into the agent's conversation, and it fixes the work or ends with failed.
The ceiling of tries is reached · a reviewer errors · a stage script exits with an errorends as failed
A stage script exits with 78ends as done; the remaining stages are skipped
minutes_per_item is used up · the run has spent cost_per_run_usd · the run is cancelledends as timed out stopped at cost cap cancelled

Nothing passes by default. Only a try that validation rejected counts against tries; a try cut short by a stopped process does not. The reviewer is a separate agent run with read-only file tools and no memory of the work.

What starts a run

A run is always a run of one flow. A person starts it, or the flow's own schedule does. A source starts nothing.

StartHowWhat happens
A personRun on the flow's page · POST /api/flows/{flow}/run · agentflow run <flow>The flow's source is fetched, and this flow alone runs over every item it accepts.
A scheduleschedule: in flow.yaml, switched on with the switch on the flow's page, POST /api/flows/{flow}/schedule or agentflow schedule on <flow>The flow's source is fetched and the flow runs. Flows on one source that are due in the same slot share the fetch. agentflow serve keeps the schedules and looks every schedule_every_seconds (30 unless set). A schedule is off until it is switched on. Missed slots count as one.
A trialagentflow try <flow> [--item ID]One item through the real stages, in a run folder of its own. Stage scripts and tools get AGENTFLOW_TRIAL=1 so they can hold back what a trial should not do.
  • The order of a run. Fetch the source into its own folder, check what it handed over, queue the items the flow accepts, work up to at_once of them in parallel, run the flow's finish script, end the run.
  • A run is just a run. Every item the flow accepts is worked, in this run's own folder. The engine does not compare a run with earlier ones. A flow that should leave out what it has already handled does that itself: its source's script hands over only what is new, where narrows the items, or a first stage script exits 78 to end an item at once. Any of its scripts can ask what earlier runs did with agentflow history [flow] [--item ID], which answers in JSON with how each item ended and where its files are.
  • Refused at the start. A flow that does not pass its checks, and a flow that uses a model whose key is not set.
  • A try that goes wrong is told, not dropped. A tool that fails or runs out of time answers the agent with its error, and the agent goes another way in the same try. A request the model did not answer is tried again by the model client. A try that still stops (the answer cut off at the output limit, out of model_calls, a CLI that exits with an error) counts as a rejected try: a fresh try gets the reason and decides whether to go on. A stage script that fails still fails the item.
  • The agent decides, the engine does not. An agent has no tool for giving up and nobody to ask. It ends a stage with {"outcome": "done" | "failed", "reason"}. Whether rejected work is done again is its decision too: it is told why in the conversation it already has. The engine retries nothing by itself except a request the model did not answer; tries is a ceiling, like a limit on turns. An item ends as done or failed.
  • What an agent is told, in layers. The base instructions (agentflow/workers/prompts/agent.md, or the flow's own file named by instructions: in flow.yaml, which replaces them), the agent's method, what the flow is for, the stage, then the task with the reasons of earlier tries.
  • Context is kept in bounds. Once a request of an agent reads more than context_tokens, the answers of its older tool calls are cleared; the calls stay, so it can ask again. Codex and Claude Code compact their own context.
  • The output is the flow's. Every run has an output/ folder. The flow's finish script runs once when every item has ended, in that folder, with the run and how each item ended as JSON on its input; stage scripts are told the folder too. The engine renders no report: it lists the folder on the run's page and serves its files. The one file it keeps there itself is run.log, a line for each thing the run did, written as the run goes. A finish script that fails does not fail the run, and a cancelled run skips it.

Models

# agentflow.yaml
models:
  luna:
    provider: openai            # openai | litellm
    name: gpt-6-luna

    reasoning: low              # none | low | medium | high

  at_once: 4
  minutes_per_item: 10
  cost_per_run_usd: 2.00

  model_calls: 20               # one agent run
  context_tokens: 100000        # past this, older tool results are cleared
  tries: 5                      # the ceiling of one stage's tries
# these seven are all the limits there are: the run and the agent loop
  • A model is a named entry under models:, with its own key variable. A litellm entry also takes base_url.
  • Picked in this order: model: on the stage, in the agent's AGENT.md, in flow.yaml, then the platform default.
  • A reviewer uses its own agent's model, then the flow's, then the default.
  • Keys come from the environment. agentflow/workers/agents.py is the only module that knows about providers.
  • The pages show no global model. The model is shown on the flow, the stage, the agent, and each try in the trace.
  • An entry with harness: hands a stage's work to a coding CLI. The next section describes it.
  • --stand-in needs no key and costs nothing. The engine's stand-in model and stand-in CLI know no flow: once per model request they ask the script the flow names as stand_in in flow.yaml what the model would do next (call these tools, done, or a reviewer's verdict). A flow without that key cannot be run on the stand-in.

A stage on a coding CLI

The engine's own harness runs a stage's agent in its process. A model entry with harness: hands the work of a stage to Codex or Claude Code instead. The engine starts the CLI in the item's work folder, waits, and keeps what it printed. It does not follow what the CLI does: the check script and the reviewer judge the files it left, as for any other try.

# agentflow.yaml
models:
  luna:       {provider: openai, name: gpt-6-luna}
  luna-codex: {harness: codex, name: gpt-6-luna,
               api_key_env: OPENAI_API_KEY}
  sonnet-cc:  {harness: claude, name: sonnet}

# flow.yaml
  - id: analyse
    agent: origin-analyst
    model: luna-codex   # this stage's work is done by Codex
  • harness is codex or claude. With api_key_env the CLI is handed that key under its own variable name. Without it the CLI uses its own sign-in.
  • A flow only names its steps. Any of them can be done by a CLI: a stage, an agent, a reviewer, a flow and the platform default can all name such a model.
  • How each CLI is started and how its output is read is in agentflow/workers/harness.py. None of it is a setting.
  • A run asks before it starts whether the CLI is installed and the named key is set.
  • --stand-in starts stand_in_cli.py in the CLI's place; it does what the flow's stand_in script says.

Every name here is defined once, in agentflow/records/layout.py. The store keeps folders relative to data/, so the data folder can be moved. events.jsonl, attempts/ and verdicts/ belong to the engine: an agent's write_file refuses them. A run id starts with r_, a trial's with t_.

A cost that was not recorded is not zero: it shows as a dash. A sum that misses a try that was cut short shows as a plain amount, and its tooltip says so.

Recovery

Nothing in agentflow/engine/recovery.py acts by itself. The watchdog records; a person or a command decides. Resume, retry and cancel stay inside one run. No run reads or continues the work of another.

PartHow it worksCommand · endpoint
Sign of lifeThe process doing a run writes a time to the run's row every heartbeat_seconds (5 unless set). A run with no ending and no sign of life for stale_after_seconds (60) shows as interrupted.
WatchdogEvery watch_every_seconds (15 unless set) inside agentflow serve, and at the start of a resume or a cancel. It closes the open tries of a quiet run as interrupted and adds an event. It never resumes and never cleans up.
ResumeTakes over an interrupted run. A run that is alive or finished is refused. An item that had ended is left alone. An unfinished item is put back on the graph where its latest try left it, in its own folder, with the reasons of its rejected tries.agentflow resume <run> · POST /api/runs/{run}/resume · Resume on the run's page
RetryOpens a finished run again for its items that did not end as done, or the one named. Each goes on at the stage where it stopped, in its own folder, told what its earlier tries said; its count of tries starts again. Items that ended as done are left alone, and the flow's finish script runs again.agentflow retry <run> [--item ID] · POST /api/runs/{run}/retry?item=… · Retry failed on the run's page
CancelIn a live run, a running stage script or check script is stopped within half a second and its item ends as cancelled. An agent finishes its try, then its item stops. A run whose process is gone is closed on the spot. Folders are kept.agentflow cancel <run> · POST /api/runs/{run}/cancel · Cancel on the run's page

Tabs are addresses: /runs/{run}/trace, /flows/{name}/files. A file of a run's output folder is at /runs/{run}/output/{file}, served sandboxed because it is the flow's page. There is no sign-in.

agentflow check                        # plugin files, settings, tool health
agentflow try <flow> [--item ID]       # a trial of one item
agentflow run <flow>                   # fetch the source, run the flow
agentflow schedule [on|off <flow>]     # show or switch schedules
agentflow serve [--port 8321]          # pages, API, schedules, tool health
agentflow show                         # recent runs
agentflow show <run> [item] [--follow] # what a run did and cost
agentflow resume <run>   agentflow retry <run> [--item ID]   agentflow cancel <run>
agentflow history [flow] [--item ID]   # for a flow's scripts: earlier runs, as JSON

try, run, resume, retry and serve take --stand-in. In the container, put docker compose run --rm in front of a command.

The engine writes only under data/. The pages and the command line read the engine; the engine never imports them.
