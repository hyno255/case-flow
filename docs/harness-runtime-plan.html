Harness Runtime Plan

A harness is the program that runs an agent's loop: it calls the model, runs tools and repeats. Today that is always the engine itself. This plan lets a stage hand its work to Codex or Claude Code on the same machine with the smallest possible layer: start the CLI, wait, read the result, the time and the cost.

This plan is built. As built lists where the code differs from the plan, and Checked and not checked says what was run. The Triage Flow Architecture page describes the result.

In short

One functionIt starts the CLI in the item's work folder with the prompt on stdin, waits, and reads the answer. About 100 lines, the same for every CLI.
One new keyharness: on a model entry. How each CLI is started, and how its output is read, is inside the engine.
Only the work is handed overThe executor of a stage can run on a CLI. The check script and the reviewer judge the files it leaves, as today.
What comes backThe CLI's last message, the seconds and the cost of the try, plus its whole output as a file in the item's folder.
The stage does not changeTries, send-back, time and cost limits, cancel and the report work as today, whoever did the work.
No number in codeThe layer adds no limit of its own. The ones that apply are already keys in agentflow.yaml.

Choosing a harness

# agentflow.yaml
models:
  luna:       {provider: openai, name: gpt-6-luna}  # the engine's own harness
  luna-codex: {harness: codex, name: gpt-6-luna}
  sonnet-cc:  {harness: claude, name: sonnet}
model: luna
# flow.yaml
stages:
  - id: analyse
    agent: origin-analyst
    model: luna-codex           # this stage's work is done by Codex
    check: scripts/chain-cites-files.py
    done_when: The origin is stated, and every link cites a file.
  • harness: on a model entry is the only new key. Its value is codex or claude. Without it the engine's own harness runs the model, as today.
  • Flows, stages and agents get no new key. They already pick a model by name, in the same order: stage, agent, flow, platform default.
  • How each CLI is started, and how its output is read, is inside the engine, in agentflow/harness.py. There is nothing to set for it.
  • A reviewer always runs on the engine's own harness, with the flow's model.

One try

stage  stages.py · unchanged around the try
  │  instructions · prompt · work folder · model · limits
  ▼

model has a harness  ─→ run_cli       the CLI as a child process behind guard.py, in the item's work folder
                          stdin   instructions, then the prompt
                          stdout  kept as attempts/<stage>-<n>.<harness>.jsonl
  │
  ▼  last message · seconds · cost
check script ─→ reviewer ─→ pass, try again, or a person   in the engine, as today

Step by step

  1. The engine builds the instructions and the prompt as today and writes attempts/analyse-1.prompt.md.
  2. For each tool the agent lists, it adds one line to the prompt: the tool's name, what it does and the command to run it.
  3. It starts the command in the item's work folder and sends the instructions and the prompt on stdin.
  4. It waits. The item's time limit and a cancel stop the CLI and everything it started.
  5. It saves the output, reads the last message and the cost, and records the try with its seconds.
  6. If the work folder now holds needs-person.md, the item ends as "needs a person" with that file as the reason.
  7. The check script and the reviewer run exactly as they do now.

The whole layer

# agentflow/harness.py
CLIS = {"codex": Codex, "claude": Claude}   # a command line, and how to read its output

async def run_cli(settings, model, instructions, prompt,
                  work, attempt_file, limits, seconds_left):
    cli = CLIS[model["harness"]]
    began = time.time()
    code, out = await run_proc(
        cli.command(model["name"], attempt_file), work,
        stdin=f"{instructions}\n\n{prompt}", env=cli.env(),
        **{**settings.proc(limits), "timeout": seconds_left})
    attempt_file.write_text(out)
    if code != 0:
        raise HarnessFailed(code, out[-limits["error_chars"]:])
    message, cost = cli.read(out, attempt_file)
    return message, cost, time.time() - began

A sketch, not the final code. run_proc and the guard are the ones scripts use today.

How the totals are recorded

The try's cost goes into the store as one model call, with the token counts when the CLI gives them. The run's sums, the cost cap, the trace and the report read that row, so none of them changes.

Reading the output

The engine does not follow what the CLI does. It asks for the work, and afterwards the check script and the reviewer judge the files in the work folder, as they do today. From the CLI's output it takes two things: the last message and the cost. Each CLI has a few lines in harness.py that pick them out.

# claude -p --output-format json prints one object
{"type": "result", "result": "origin.md is written.",
 "total_cost_usd": 0.0412, "duration_ms": 38211,
 "usage": {"input_tokens": 18420, "output_tokens": 1630}}

The last message is result. The cost is total_cost_usd.

# codex exec --json prints an event per line; the last ones:
{"type": "item.completed", "item": {"type": "agent_message",
 "text": "origin.md is written."}}
{"type": "turn.completed",
 "usage": {"input_tokens": 21034, "output_tokens": 1890}}

The last message is in the file written with -o. The output has tokens and no cost.

The numbers in both examples are made up to show the shape. The field names are from each tool's documentation.

Why tokens are read at all

Only to know the cost. Claude Code reports its cost. Codex reports tokens and no cost, so its cost is the tokens times the engine's price for the model, the same sum the engine's own harness does. Tokens are nothing you set.

Limits

The layer adds no setting under limits, engine or show. These existing ones apply to a try on a CLI.

SettingOn a CLI
limits.minutes_per_itemStops the CLI when the item runs out of time. It is also the CLI's own time limit.
limits.cost_per_run_usdChecked before each stage, as today, on the cost recorded for earlier tries.
limits.tries, max_triesAs today.
limits.error_charsHow much of a failed CLI's output is kept as the reason.
limits.event_charsHow much of the answer is kept in the trace. The whole output is in the file.
engine.stop_grace_seconds, poll_secondsFor stopping the CLI, as for scripts.
limits.model_calls, read_chars, tool_chars, script_secondsDo not apply. The CLI counts its own calls and reads files with its own tools.

What you give up

Given upWhat you have instead
A step-by-step traceOne line per try with seconds, tokens and cost, and a link to the CLI's whole output.
Plugin tools as real toolsThe prompt names each tool's command, and the CLI runs it with its own shell. A tool that needs a granted secret, and a tool that is an MCP server, do not work on a handed-over stage. agentflow check says so for each stage it affects.
The engine policing the CLIThe CLI's own sandbox flag keeps writes in the work folder. The engine does not verify it. Inside the container, the container is the boundary, as it is for scripts.
A clean setup per tryThe CLI runs with your home folder, so it uses your sign-in. It also reads your own CLAUDE.md, AGENTS.md and settings. A flag on the command line can switch that off.
Changing a CLI without codeThe command lines are in harness.py. Another flag is a one-line change there, and another CLI is a few lines.
ask_for_person as a toolA file. The instructions say to write needs-person.md when the files cannot settle the stage.
A reviewer on a CLIThe reviewer stays on the engine's own harness, read-only, with its typed verdict.
